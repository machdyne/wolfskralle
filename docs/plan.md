# Wolfskralle firmware: development plan

Status: **phases 1-5 implemented and working on hardware: an LS10A
(CH32V003) is flashed and verified in 8.4 s. Open: the remaining hardware
tests of phases 1-5 (docs/hwtest.md), above all the CH32V005 (LS11A);
then phase 6.**

## Goal

New firmware for the Wolfskralle's CH32V003, written from scratch, that
programs Zwölf modules (LS10A: CH32V003, LS11A: CH32V005) through the
spring contacts reliably over USB, plus a host tool, `wolfctl`. It follows
the same rules as the Werkzeug programmer in machdyne/basic
(`docs/ch32prog.md`): main flash only, never the option-byte key, the right
chip, the right image, verified before release, always recoverable.

## Findings that shape the design

1. **Only 2 KB of RAM.** Werkzeug receives the whole image before touching
   the module; Wolfskralle cannot. The host keeps the image and the
   policy, and the firmware works one page at a time. The firmware keeps
   its own write gate (main flash and the flash controller registers only),
   so a host bug still cannot write the option bytes.
2. **No target reset on v0.** TRESET is not connected to the MCU on v0 (a
   hardware bug, fixed in v1). The firmware supports both boards
   (`BOARD_V0`, `BOARD_V1` in `board.h`). On v0 a job starts with a power
   cycle of the target (PD2) and then connects and halts; this is enough
   for the chips v0 programs: factory-new chips, whose debug interface is
   enabled, and modules running Machdyne BASIC, which keeps SWIO on. On v1
   the target is held in reset and halted before its firmware runs, as on
   Werkzeug, which also recovers firmware that turns SWIO off.
3. **USB is bit-banged at low speed (rv003usb).** No CDC on Windows/macOS
   (low speed has no bulk endpoints), so HID it is. The USB interrupt must
   never be blocked for more than a few microseconds, so SWIO has to be
   generated by TIM2 and DMA, not by the CPU with interrupts off.
4. **Likely causes of the current unreliability** (to be confirmed in
   phase 0):
   - H1, SWIO margin: the existing firmware makes a "1" about 290 ns low
     (its own comment), open drain, with a 5K1 pull-up. On an LS10A the
     window for a 1 ends near 300-350 ns (machdyne/basic measurements), so
     the slow rising edge through the spring contacts can push a 1 out of
     the window. **Measured (round 3b): does not hold.** The line rises
     within about 2 ticks (40 ns), and a 1 works up to about 520 ns on
     the line (docs/swio.md).
   - H2, USB protocol: the request/response over feature reports has no
     sequence numbers or checksums, and the host cannot tell a lost reply
     from a stale one.
   - H3, power: switching on target power charges 10 uF from the same 3.3V
     rail as the MCU; the dip may upset USB or the MCU.

## Phases

Each phase ends with a hardware gate. Documentation in `docs/` is updated
in every phase.

### Phase 0: characterise (with the existing firmware)
Reproduce the failures and sort them into H1-H3 (or others): kernel log for
USB errors, a scope on TSWIO (pulse widths, rise time), and on 3V3 while
target power switches. Deliverable: `docs/hwtest.md` with the results.
If no scope is available, this phase is folded into phases 1 and 2.

### Phase 1: skeleton, USB and protocol (round 1: done, hardware tests pending)
- `firmware/`: ch32fun + rv003usb (pinned versions), `board.h`, LED,
  target power on/off.
- HID with vendor feature reports; protocol with a sequence number, length
  and CRC on every request and reply; replies are kept until the next
  request, so a lost reply is fetched again rather than the command run
  twice; a "busy" status instead of stalling USB.
- `host/wolfctl` (C, Linux hidraw, no dependencies): `info`, `power`,
  `led`, `ping N`.
- Gate: 100,000 pings without an error, also while target power is cycled.

Done in round 1: `firmware/` (docs/firmware.md), `common/wkproto.h` and
the protocol (docs/protocol.md), `host/wolfctl` (docs/wolfctl.md), the
protocol test with injected faults (`make -C host test`). Added beyond the
plan: the supply voltage measured against the internal reference, and
`wolfctl power on -m`, which watches it while target power switches on
(H3 without a scope); a serial number from the chip's unique ID, so
several Wolfskralles can be told apart. Decided: 128-byte reports (to be
revisited in phase 5 with measurements), VID:PID 1209:0001 (the pid.codes
test PID) until a PID is assigned, the interrupt endpoint NAKed with the
longest interval.

### Phase 2: SWIO link (round 2: done, hardware tests pending)
- TIM2 + DMA SWIO engine on PC1/PC2, timing in timer ticks (20.8 ns), USB
  interrupts always enabled.
- Calibration: sweep the width of a 1 and a 0 with a link test and settle in
  the middle of the working window; `wolfctl swio-timing` and
  `swio-scan` show it.
- `wolfctl swio-test N` (write and read back a debug register, as
  `sechsctl swio-test`).
- Gate: 10,000 round trips without an error on an LS10A and an LS11A in the
  spring contacts, with USB pinged at the same time; the window recorded.

Done in round 2: `firmware/swio.c` (TIM2 CH2 PWM out on PC2, CH4 capture in
on PC1, two DMA channels), docs/swio.md; commands SWIO, SWIO_TIMING, DMI
(batches of up to 20 register operations, the base for phase 3),
SWIO_TEST, SWIO_RAW (protocol version 2); `wolfctl swio`, `swio-timing`,
`swio-test [--load]`, `swio-scan [--apply]`, `swio-raw`, `dmi`. Every bit
comes back as a measurement of its low time, so the rise time (H1) is
measured on every packet, without a scope. Mode 1 drives write packets
push-pull, for fast edges where the chip never answers. The packet format
follows the one proven on hardware by machdyne/basic (41 bits, no
parity); `make -C host test` checks the encoding against it. The timing
is in RAM; the defaults will be set from the scan results.

### Phase 3: debug access, read-only (round 3: done, hardware tests pending)
- Connect, halt, identify (chip ID, hartinfo), resume; a power cycle
  before each job (v0), reset-and-halt (v1).
- `wolfctl id`, `wolfctl read addr len` (flash dump), device-side CRC32
  of a range.
- Gate: correct IDs on factory-new CH32V003 and CH32V005 modules and on
  modules running BASIC; a dump that matches the file flashed with a
  WCH-LinkE. (Recovery of firmware that turns SWIO off: v1 only.)

Done in round 3: `firmware/ch32dbg.c` (docs/debug.md), hardware-independent,
with the sequences of machdyne/basic's ch32prog; commands CONNECT (auto,
attach, restart), RESUME, MEM_READ, CRC32 (protocol version 3);
`wolfctl id`, `read`, `crc`, `resume`. In auto mode the Wolfskralle
attaches first and power-cycles only if nothing answers. `wolfctl read`
reads everything twice (the second time as a CRC on the device). Tested
against a simulated CH32V003 and CH32V005 (`host/test/chipsim.h`, adapted
from basic's): connecting, the power-cycle catch of a program that turns
SWIO off, identification, whole-flash reads and CRCs, read protection,
damaged packets (a read is right or fails, never wrong), and no memory
write ever. The chip's identity is decided on the host, from raw values
the device reports.

### Phase 4: programming (round 4: done, hardware tests pending)
- Firmware: erase/program/verify one page from its buffer, with the write
  gate; CRC32 of the whole flash on the device, so the image is not read
  back over USB.
- Host: `ch32prog` from machdyne/basic adapted to page operations, with
  the same rules (rule 5 on v0: power cycle, connect and halt before any
  erase; on v1: through RESETN); the simulated
  CH32V003/CH32V005 from basic for tests, behind a simulated Wolfskralle.
- `wolfctl flash ls10.bin`, `--force` for non-BASIC images.
- Gate: complete flashes on both modules; USB unplugged and target power
  cut at random points, each followed by a successful flash.

Done in round 4: the write gate and page programming in
`firmware/ch32dbg.c` (the sequences of machdyne/basic's ch32prog); the
debug and flash commands moved to `firmware/dbgcmds.c`
(hardware-independent) with new ones FLASH_BEGIN, PAGE_LOAD, PAGE_WRITE,
FLASH_END (protocol version 4, firmware 0.6); the job with the failsafe
rules in `host/flash.c`; `wolfctl flash` and `verify`; docs/programming.md.
Different from basic: the image stays on the computer (2 KB of RAM), the
gate is in the Wolfskralle, pages that already hold the right data are not
erased, and damaged SWIO packets are repeated where that is safe. Tests:
`host/test/flash_test.c`, the whole path from wolfctl to a simulated chip
with a strict flash controller, with refusals, the gate on its own,
damaged packets and about 270 power cuts.

### Phase 5: speed (rounds 5 and 5b: done; 8.4 s on hardware)
Program-buffer flash loop and auto-execution in the debug module, larger
reports if measurements allow. Target: a 16 KB module in under 10 s with
full verification.

Done in round 5 (docs/programming.md, speed): the pages compared first
on the Wolfskralle (VERIFY_PAGES) so only differing pages travel; a
CH32V003 page inside PAGE_WRITE; faster polling during a flash; fast
reads and page programming with auto-execution (checked when connecting
and by every page verify, dropped if wrong, switched off and read back
after use, inside the gate); one ABSTRACTCS check per access; `--slow`.
In simulation: 55,000 debug transactions and 270 USB requests for a
12 KB CH32V003 flash (before 150,000 and 450). Not done: larger reports
(the remaining USB time is small now), a shorter SWIO bit (needs a scan).

### Phase 6: Sechs and extras
- I2C on PC5/PC6: `wolfctl sechs scan/info`; put an LS11 into programming
  mode through Sechs before flashing; after a flash, check that the module
  answers with the new firmware.
- Updating the Wolfskralle itself over USB (rv003usb bootloader), and
  programming a second Wolfskralle through J2.
- Later, if wanted: CH32V2xx/V3xx (two-wire, SWCLK on ZP1).

## Board v1

TRESET will be connected to the MCU (a free pin: PC0, PC3, PC4 or PC7,
through a resistor; the pin goes into `board.h` once v1 is drawn). Also
worth considering: a stronger pull-up on TSWIO (1K-2K2), and a soft start
or separate regulator for target power.

## History

- Round 0: proposal, hardware notes (`docs/hardware.md`).
- Round 0, revised: TRESET is a v0 hardware bug, fixed in v1; v0 programs
  factory-new chips, so it uses a power cycle instead of a reset; the
  firmware supports both boards.
- Round 1: phase 1 implemented (firmware, protocol, wolfctl, tests, CI).
- Round 2: phase 2 implemented (SWIO with TIM2 and DMA, timing scan, link
  test with measured pulses; protocol version 2, firmware 0.2).
- Round 3: phase 3 implemented (connect, power-cycle catch, identify,
  read, CRC, resume; protocol version 3, firmware 0.3).
- Round 3b: the first SWIO measurements on hardware (swio-scan): SWIO
  works, wide margins, H1 ruled out; defaults set from them (firmware
  0.4); swio-scan scans the read pulse separately and prints clearer.
- Round 3c: second scan confirms the ranges; a timeout in a long scan led
  to: link tests in short commands, gentler polling of a busy device,
  timeouts that say why, a watchdog with the reset cause in INFO
  (firmware 0.5).
- Round 4: `wolfctl id` works on hardware (phase 3). Phase 4 implemented:
  programming with the failsafe rules (protocol version 4, firmware 0.6).
  First flash on hardware: an LS10A, 16 KB, verified, 23.3 s; again 9.4 s.
- Round 5: phase 5 implemented (speed; protocol version 5, firmware 0.7).
  On hardware: 10.6-10.9 s for a full CH32V003 (before 23.3 s).
- Round 5b: short USB replies and requests (a BUSY answer: one packet
  instead of sixteen), no page read before writing a page known to
  differ, PROFILE (protocol version 6, firmware 0.8). On hardware: 8.4 s
  for a full CH32V003; phase 5 closed. Where the rest goes, should it
  ever matter: programming 2.7 s, erasing 1.9 s, CRCs 1.3 s, USB 1.8 s
  (a shorter SWIO bit, cheaper busy polls, larger reports).
